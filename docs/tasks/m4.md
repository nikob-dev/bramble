# M4 — Three pet-banks, a network, and two payment rails

**Goal:** three pet-banks on one machine pay each other over two rails:
- **RTP:** instant, each payment settled on its own ("gross")
- **ACH:** batched; what the banks owe each other is netted at a cutoff time and settled once

The learner investigates both from the lab.

**Definition of done (from the roadmap):** ACH nets correctly at cutoff, and all ledgers reconcile across banks.

**Branch:** `feat/m4-rails`. It's stacked on `feat/m2-teacher` until PRs #1 and #2 merge; then rebase onto `main`.

## Decisions: answer these before starting the loop

Each one has my recommendation. Edit the **Answer** line: write `ok` to accept, or your choice. The loop won't start a task that depends on an unanswered decision.

### D1. How do pets talk to each other?
- **Recommended: signed messages over plain HTTP between containers**, with a static peer list (`BRAMBLE_PEERS=pet-b:8080,pet-c:8080`; compose gives each container a DNS name).
  - Message signing, replay protection and versioning stay in scope; that's the part worth teaching.
  - libp2p (a peer-to-peer networking library) is deferred to M5, where gossip between many reviewers actually needs it.
- **Alternative: libp2p gossipsub + mDNS discovery**, as the roadmap says today.
  - It's a heavy dependency, mDNS is known to be flaky on Docker networks, and the payments lessons gain nothing from it.
- This deviates from `docs/roadmap.md`, so the loop records it as decision 011.

**Answer:** ok

### D2. Who settles between the banks?
- **Recommended: a 4th container, `operator`**, which plays the central bank / clearing house.
  - It's the same binary as the pets: `bramble node --role operator`.
  - It holds each bank's reserve account, moves reserves instantly for RTP, and nets ACH at cutoff.
  - This mirrors reality: the Fed for ACH, The Clearing House for RTP. Disagreements between banks show up as an operator-vs-bank mismatch the learner can find.
- **Alternative: banks settle bilaterally**, with no operator. Simpler, but it teaches the wrong model.

**Answer:** ok

### D3. When does ACH cutoff happen?
- **Recommended:** a manual trigger, plus an optional timer.
  - Manual: `bramble ach cutoff`, run by the learner or a lesson.
  - Timer: `BRAMBLE_ACH_CUTOFF_SECS`, off by default. Tests stay deterministic, and lessons control when it happens.
- **Alternative:** a wall-clock cutoff every N minutes. More realistic, but harder to test and to teach with.

**Answer:** ok

### D4. What do ACH files look like?
- **Recommended: a real Nacha subset**, 94-character fixed-width records:
  - file header (1), batch header (5), entry detail (6), batch control (8), file control (9)
  - including entry hash and total checks

  Learners inspect real-looking files with `cat`, `cut` and `awk`, which is genuinely useful knowledge.
- **Alternative:** JSON. Easier to build, but it teaches nothing about ACH.

**Answer:** ok

### D5. What does the learner see?
- **Recommended:**
  - `pet-a` (pip) is *your* bank: `make play` attaches to it, as today.
  - `pet-b` and `pet-c` are counterparties, each with its own dashboard on :8082 and :8083.
  - The operator has a read-only dashboard on :8090.
  - Only `pet-a`'s lab is used in lessons.

**Answer:** ok

### D6. What's in the Rails track?
- **Recommended: 4 lessons**, each citing primary sources (Nacha, the Fed's FedACH pages, The Clearing House RTP):
  1. *Instant payments (RTP):* send money to a customer at pet-b; watch reserves move at once; finality.
  2. *Batch payments (ACH):* originate entries, inspect the Nacha file, run cutoff.
  3. *Netting & settlement:* why 6 payments became 1 settlement; compute the net position with SQL.
  4. *Cross-bank reconciliation:* find a planted break between your books and the operator's.
- **Plus a cutaway:** RTP vs ACH on speed, cost, finality, failure modes and float.

**Answer:** ok
